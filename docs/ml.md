# ML / LLM подход

## Что решается правилами, а не ML
- Обнаружение PII (email, телефон, номер карты) — детерминированные регэкспы (`app/guard.py`). ML здесь не нужен: паттерны структурные, ложноположительные срабатывания дешевле и предсказуемее регэкспа, чем модели.
- Обнаружение prompt injection — эвристика по ключевым фразам. Это первый рубеж, не заменяет полноценную защиту (см. `docs/risks-and-ops.md`), но не требует модели.
- Жёсткая эскалация денежных/security-категорий — бизнес-правило (`RISKY_CATEGORIES` в `app/router.py`), не решение модели: цена ошибки для этих категорий асимметрична (потеря денег/доступа), автоматизировать нечего — решение всегда "эскалировать".

## Где классическая ML-модель / embeddings-retrieval
- **Классификация категории тикета** — cosine similarity (TF-IDF) входящего текста к few-shot примерам категорий (`app/classifier.py`). Это классический baseline, не LLM: задача — многоклассовая классификация короткого текста, для которой полноценная генеративная модель избыточна по стоимости и латентности на hot path (≤500мс).
- **Retrieval релевантного FAQ-документа** — та же механика similarity, применённая к базе знаний (`app/rag.py`). Задача поиска ближайшего документа не требует LLM — LLM нужен только на следующем шаге, чтобы превратить найденный фрагмент в связный ответ.

## Где нужен LLM
- **Генерация черновика ответа** пользователю на основе найденного FAQ-фрагмента (`app/llm_client.py`) — единственное место, где естественно-языковая генерация оправдана: нужно связать контекст и вопрос в читаемый ответ, а не просто вернуть документ целиком.
- В PoC — детерминированный `MockLLM` (не требует ключа, воспроизводим); в проде — реальный провайдер за тем же интерфейсом `LLMClient`.

## Где LLM использовать не стоит
- **Классификация и маршрутизация на hot path** — LLM здесь означало бы латентность и стоимость на каждый из ~200k тикетов/день ради задачи, которую решает cosine similarity на few-shot примерах. Не наш случай.
- **Принятие решения по риск-категориям** — LLM не должен решать, отправлять ли ответ по `billing_refund`/`account_access`: это бизнес-правило, не ML-задача, и цена ошибки слишком высока для делегирования модели.
- **Ответ при низкой уверенности retrieval** — если релевантного FAQ-документа нет, генерировать ответ без опоры на контекст — прямой путь к галлюцинации. В этом случае — эскалация, а не "додумывание" LLM.

## Baseline, который запускаем первым
До любого ML — простой lookup: точное/подстрочное совпадение текста тикета с FAQ. Он не установлен как отдельный шаг в PoC, но именно поэтому первым реальным шагом стал TF-IDF + cosine similarity — минимальная модель, которая уже покрывает перефразированные запросы, а не требует обучения или разметки большого датасета.

## Валидация без большого датасета
Датасет `data/eval/sample_tickets.jsonl` — 18 вручную составленных примеров, по 3 на категорию, из разных каналов. Прогон классификатора на нём:

| Метрика | Значение |
|---|---|
| Accuracy | 16/18 = 89% |
| Ошибки | 2 (см. ниже) |
| Confidence верных предсказаний | 0.58 – 1.00 |
| Confidence ошибочных предсказаний | 0.37 и 0.45 |

Обе ошибки классификации: "мой аккаунт заблокирован без объяснения причин" (ожидалось `account_access`, получено `order_status`, conf 0.449) и "подскажите, как работает программа лояльности" (ожидалось `other`, получено `technical_bug`, conf 0.367).

Порог `CONFIDENCE_THRESHOLD` изначально стоял на 0.35 (взят "на глаз"); прогон на eval-датасете показал, что он не отсекает ни одну из двух реальных ошибок. Подняли до **0.5** — на этом наборе порог ровно отделяет обе ошибки (confidence < 0.5) от всех 16 верных предсказаний (confidence ≥ 0.58), то есть при пороге 0.5 обе ошибки уходят в эскалацию вместо неверного автоответа, а верные предсказания не теряются. На 18 примерах это наблюдение, а не доказанная закономерность — при расширении eval-датасета порог нужно пересчитать.

## Обработка низкой уверенности
`confidence < CONFIDENCE_THRESHOLD` → эскалация (см. `app/router.py`), тот же принцип, что и для риск-категорий и PII/injection. Явного отдельного порога для confidence самого retrieval (в `rag.py`) в PoC нет — упрощение; в проде стоило бы эскалировать и в случае низкой similarity найденного FAQ-документа, а не только низкой уверенности классификатора.

## Происхождение моделей и данных
- В PoC не используется ни одна скачиваемая/обученная модель — только `scikit-learn TfidfVectorizer`, обучаемый на лету на few-shot примерах и на FAQ-корпусе, без внешних весов и без PII в обучающих данных.
- Few-shot примеры категорий (`EXEMPLARS` в `app/classifier.py`) написаны вручную, не из реальных исторических тикетов — их нет в PoC-окружении.
- В проде: дообучение/калибровка на исторических тикетах потребует (1) процесс разметки — например, использовать финальную категорию, которую оператор проставил вручную, как метку; (2) удаление/маскирование PII из текста тикета перед использованием для обучения или для embeddings; (3) периодическая переразметка при дрейфе тематики (см. `docs/monitoring.md`).
- Technical-метрика выбора модели классификации в проде — F1 по категориям (не accuracy, т.к. классы несбалансированы: `billing_refund`/`account_access` реже, чем `order_status`) плюс calibration ошибки confidence (Brier score) — важно, чтобы порог эскалации был откалиброван, а не произволен.
