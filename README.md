# Автоматизация обработки тикетов поддержки — System Design Case

PoC системы, которая принимает тикет поддержки, определяет тему и риск, находит релевантный фрагмент базы знаний, предлагает черновик ответа (happy path) либо отправляет тикет оператору без автоответа (risky/fallback path), и логирует каждое решение для аудита.

Полный дизайн — в `PLAN.md` (что и почему) и `docs/` (архитектура, ML-подход, мониторинг, риски). Этот README — только "как запустить" и краткая сводка.

## Как запустить

```bash
python -m venv .venv
source .venv/Scripts/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt

uvicorn app.main:app --reload      # поднимет API на http://localhost:8000
pytest -q                          # smoke-тесты: happy / escalation / llm-fallback
python scripts/demo.py             # запустить 2 сценария на живом API (сервер должен быть поднят)
```

Или через Docker:
```bash
docker compose up --build
```

Проверить руками:
```bash
curl -X POST localhost:8000/tickets -H "Content-Type: application/json" \
  -d '{"ticket_id":"t1","customer_id":"c1","channel":"chat","text":"когда приедет мой заказ?"}'
```

## Что реально реализовано, а что — дизайн

**Реализовано (PoC):** FastAPI-эндпоинт, PII/prompt-injection эвристики, baseline-классификатор (TF-IDF + cosine similarity к few-shot примерам), retrieval по мини-базе FAQ (та же TF-IDF-механика), мок LLM с имитацией сбоя и деградацией, роутинг auto-reply/escalation, идемпотентность по `ticket_id`, in-memory audit log, smoke-тесты.

**Дизайн, не реализовано (описано в `docs/architecture.md`):** очередь для амортизации всплесков нагрузки (10–20k тикетов/10 мин при инцидентах), горизонтальное масштабирование воркеров, persistent-хранилище и отдельный append-only audit log, managed vector DB и embeddings вместо TF-IDF, реальный LLM-провайдер вместо мока, дедупликация/кластеризация тикетов во время инцидентов, полноценный мониторинг и алертинг.

## Допущения
- Тикет: `ticket_id`, `customer_id`, `channel` (chat/email/web/app), `text`.
- Категории: `order_status`, `account_access`, `billing_refund`, `technical_bug`, `abuse_or_complaint`, `other`.
- Автоответ разрешён только для информационных, не денежных и не связанных с безопасностью категорий (`order_status`, часть `technical_bug`), покрытых базой знаний.
- Жёсткая эскалация на человека: `billing_refund`, `account_access`, `abuse_or_complaint`, низкая уверенность классификатора, обнаруженный PII, признак prompt injection, недоступность LLM без canned-ответа для категории.

## Зачем это бизнесу
Сервис получает ~200k тикетов/день, из которых ~40% — типовые повторяющиеся обращения; при цене обработки оператором ≈150₽/тикет автоматизация даже части этого потока напрямую снижает операционные затраты и время первого ответа (текущий SLA — 15 мин). Ценность — не в автоматическом закрытии всего подряд, а в том, чтобы освободить операторов от рутины и одновременно не дать модели самостоятельно принимать решения там, где цена ошибки высока (деньги, доступ к аккаунту, жалобы) — такие тикеты всегда уходят человеку с сохранением SLA и без риска для CSAT (сейчас 4.2/5) и reopen rate (сейчас 9%). Во время инцидентных всплесков (10–20k тикетов/10 мин) система также даёт основу для дедупликации однотипных обращений, снижая нагрузку на поддержку именно тогда, когда она критична. Итог — быстрее типовые ответы, безопаснее рискованные, и полная аудируемость автоматических решений для последующего разбора.
