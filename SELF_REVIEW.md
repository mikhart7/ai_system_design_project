# SELF_REVIEW

**Самое слабое место**: категории тикетов я придумал сам, без реальных данных — на практике они могут быть другими. Классификатор обучен на 3-4 примерах на категорию, а eval-датасет всего 18 строк — 89% точности на таком объёме мало что доказывает.

**Допущения**: список категорий и правило "что эскалируем всегда" не согласованы с реальной командой поддержки. Порог уверенности 0.5 подобран на 18 примерах, не на исторических тикетах.

**Что не решено**: PII и prompt injection ловятся только регэкспами по известным паттернам — обходятся перефразированием. Для поиска по базе знаний нет отдельного порога уверенности (только для классификации). Дедупликация тикетов при массовых сбоях — только описана, не сделана.

**Что доделать за 2 дня**: собрать eval-датасет побольше (100+ реальных обезличенных тикетов) и пересчитать порог; добавить порог уверенности для retrieval; сделать простую очередь и проверить систему на симуляции всплеска нагрузки.

**Перед запуском в продакшн**: заменить память на БД с логом, который нельзя изменить задним числом; заменить TF-IDF на embeddings, обученные на реальных тикетах; подключить настоящий LLM с повторными попытками при сбое; провести нагрузочный тест на заявленный пик.

**Что нельзя автоматизировать полностью**: решения по деньгам и доступу к аккаунту — цена ошибки слишком высокая. Ответы на жалобы — шаблонный ответ может разозлить человека ещё больше.

**Что заставило бы меня остановить проект**: если после пилота reopen rate вырастет выше 9% или CSAT упадёт ниже 4.2 именно на автоответах — значит система создаёт видимость решения без реальной пользы, и масштабировать дальше нельзя.
