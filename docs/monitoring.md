# Мониторинг

## Технические метрики
- Latency hot path (guard + classifier) — P50/P95/P99, алерт при выходе за ориентир 500мс.
- Latency slow path (retrieval + LLM generation), отдельно от hot path.
- Throughput (тикетов/сек) и глубина очереди/backlog — особенно важно на всплесках 10-20k/10мин.
- Error rate API (5xx), LLM timeout/error rate отдельно от прочих ошибок — это сигнал для circuit breaker.

## ML-метрики
- Распределение confidence классификатора по времени (гистограмма/percentiles) — резкий сдвиг вниз может значить деградацию модели или смену входящего потока (см. ниже).
- Доля тикетов ниже `CONFIDENCE_THRESHOLD` (эскалация по low-confidence) — рост доли = либо модель "не справляется", либо появился новый тип обращений, которого нет в few-shot примерах/FAQ.
- Reopen rate именно для auto-reply тикетов (отдельно от общего reopen rate) — прокси качества автоответов без ручной разметки: если пользователь переоткрыл тикет после автоответа, ответ, скорее всего, не решил проблему.
- Distribution retrieval-similarity (насколько близко найденный FAQ-документ к запросу) — низкая similarity даже при "уверенной" категории — риск нерелевантного ответа.

## Бизнес-метрики
- **North star**: доля тикетов, закрытых автоматически без оператора (deflection rate), без ухудшения CSAT относительно текущего 4.2/5.
- **Guardrails**: reopen rate (не должен расти выше текущих 9% для авто-обработанных тикетов), CSAT (не ниже текущего для авто-обработанных тикетов), SLA breach rate (доля тикетов, не получивших первый ответ за 15 минут).
- Экономический эффект — количество тикетов/день, закрытых автоматически × 150₽ (проксирует высвобожденное время оператора) — как индикатор ценности, не как основной KPI.

## Мониторинг стоимости LLM
- $/₽ на тикет (генерация) и суммарные траты за день/неделю, с бюджетным порогом и алертом при приближении.
- Доля тикетов, дошедших до LLM-вызова (после guard+classifier+risky-фильтра) — если доля растёт быстрее объёма трафика, значит либо ослабли фильтры, либо изменился состав тикетов.
- Учитывать отдельно: обычный трафик vs всплеск-инцидент — без дедупликации (см. `docs/architecture.md`) стоимость на инцидентах может вырасти нелинейно (много почти одинаковых тикетов).

## Как отличить деградацию модели от изменения входящего потока
- Если распределение confidence падает **при стабильном распределении категорий** (доли category mix не изменились) — похоже на деградацию модели/устаревание few-shot примеров.
- Если распределение confidence падает **одновременно со сдвигом category mix** (резко выросла доля одной категории, например `technical_bug` во время сбоя) — это, скорее, изменение входящего потока (инцидент, новая тема обращений), не деградация модели. Требует новых few-shot примеров / FAQ-документов, а не переобучения.
- Практически: логировать оба распределения (confidence и category mix) с одинаковой периодичностью и сравнивать сдвиги синхронно, а не только смотреть на среднюю confidence.

## Стартовые алерты
- Latency hot path P95 > 500мс за 5 минут подряд.
- Error/timeout rate LLM API > 10% за 5 минут — триггер circuit breaker + оповещение.
- Доля low-confidence эскалаций выросла > 2x от недельной базовой линии.
- Дневные траты на LLM превысили заданный бюджет.
- Escalation queue backlog растёт быстрее, чем обрабатывается (по числу необработанных тикетов) — риск нарушения SLA.

## Как проверяем, что решается именно исходная задача
Раз в отчётный период (например, неделя) — сверять north star и guardrail-метрики: если deflection rate растёт, а CSAT/reopen rate не ухудшаются — система решает исходную задачу (снижает нагрузку без потери качества). Если deflection rate растёт вместе с ухудшением guardrail-метрик — это сигнал остановить автоматизацию расширяться (см. также `SELF_REVIEW.md`, вопрос про данные, которые остановили бы проект).
