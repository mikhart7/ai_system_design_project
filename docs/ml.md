# ML / LLM подход

## Что решают правила
- Поиск PII (email, телефон, номер карты) — регэкспы, ML не нужен.
- Поиск prompt injection — список ключевых фраз.
- Жёсткая эскалация денежных/security-категорий — бизнес-правило, не решение модели: цена ошибки слишком высока, чтобы отдавать её ML.

## Где классическая ML/retrieval
- **Классификация категории тикета** — cosine similarity (TF-IDF) к нескольким примерам на категорию. Это простой baseline, а не LLM: задача короткая, для hot path (≤500мс) LLM избыточен.
- **Поиск нужного FAQ-документа** — та же similarity, применённая к базе знаний.

## Где нужен LLM
Только для одного шага — превратить найденный FAQ-фрагмент в связный ответ пользователю. В PoC это мок (без реального ключа/API), в проде — заменяется реальным провайдером.

## Где LLM не нужен
- На классификации/маршрутизации — дорого и медленно ради задачи, которую решает cosine similarity.
- На решении по риск-категориям — это правило, не ML.
- Если релевантного FAQ не нашли — генерировать ответ без опоры на факты означает риск галлюцинации, поэтому эскалация.

## Как проверяли качество (без большого датасета)
Собрали 18 примеров тикетов вручную (`data/eval/sample_tickets.jsonl`), по 3 на категорию. Прогнали классификатор:
- **16 из 18 верно** (89%).
- 2 ошибки — уверенность модели была низкой (0.37 и 0.45).
- Порог отсечения (`CONFIDENCE_THRESHOLD`) сначала стоял на 0.35 "на глаз" — он не отсекал обе ошибки. Подняли до **0.5**: на этом наборе порог ровно отделяет 2 ошибки от 16 верных ответов (у них уверенность ≥ 0.58).

Ниже порога — тикет уходит оператору, а не в автоответ. Это тот же принцип, что и для риск-категорий и PII.

## Откуда модели и данные
Модель ничему не обучена — только TF-IDF, который считается на лету по нескольким вручную написанным примерам. Реальных исторических тикетов в PoC нет. В проде: нужна разметка (например, финальная категория, которую проставил оператор) и обязательное удаление PII из данных перед обучением/индексацией.
