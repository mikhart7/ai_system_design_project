# Риски и эксплуатация

## Highload и надёжность
- Fast path (guard + classifier) синхронный и дешёвый (regex + TF-IDF, без сети) — держит ориентир ≤500мс независимо от нагрузки на LLM; slow path (retrieval + генерация) в PoC вызывается синхронно в том же запросе ради простоты, в целевой архитектуре — асинхронно через очередь (см. `docs/architecture.md`).
- Пики нагрузки при инцидентах (10-20k тикетов/10мин, до ~14x от базового потока) требуют очереди между приёмом и обработкой и автоскейлинга воркеров — без этого fast path деградирует вместе со slow path. В PoC это спроектировано, но не развёрнуто.
- Недоступность LLM API не должна ронять обработку тикетов: в PoC `router.py` перехватывает `TimeoutError` и либо отдаёт canned-ответ по категории, либо эскалирует с причиной `llm_unavailable` — тикет никогда не "зависает" без ответа.
- Идемпотентность по `ticket_id` реализована в PoC (повторный запрос с тем же id возвращает сохранённый результат, не создаёт дубликат) — необходимое условие для retries без дублей при работе через очередь с at-least-once доставкой.

## Privacy, safety и risk
- PII (email, телефон, номер карты), обнаруженный в тексте тикета, блокирует автоматическую обработку — тикет уходит на эскалацию, не в LLM-промпт (`app/guard.py`). Это защищает от отправки персональных данных во внешний LLM API, но эвристика (regex) не покрывает все формы PII — не полагаться как на единственный механизм в проде.
- Автоматически не закрываются категории, где цена ошибки высока: `billing_refund` (деньги), `account_access` (доступ/безопасность), `abuse_or_complaint` (эскалация конфликта) — всегда human-in-the-loop, независимо от уверенности модели.
- Prompt injection — эвристика по ключевым фразам (`app/guard.py`) ловит только известные паттерны ("ignore previous instructions" и т.п.); это первый рубеж, не полноценная защита — обходится перефразированием. В проде нужен отдельный, регулярно обновляемый слой защиты и/или sandboxing промпта.
- Каждое автоматическое решение (категория, confidence, путь, флаги, причина эскалации) пишется в audit log (`app/storage.py`) — основа для последующего аудита и разбора инцидентов; в PoC лог in-memory и не персистентный, в проде — append-only хранилище.
